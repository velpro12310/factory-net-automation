# 智能工厂网络 · 配置即代码与可达性验证

一个把**网络配置当代码管**的工程：拓扑与安全策略写在一份 YAML 里，
一键生成 6 台华为设备的 VRP 配置，再自动推导 2100 个流量组合的
「通 / 不通」结论，与设计意图逐条比对，最后故意把拓扑改坏来证明校验能力有效。

不依赖 eNSP、GNS3 等模拟器，也不依赖任何设备——**纯靠拓扑数据推导**，
所以它能进 CI，也能在改配置**之前**先做一次变更预演。

```
实测结果（Python 3.13 / Windows）
  pytest                  51 passed in 0.69s
  用例总数                50 / 50 通过
  校验能力覆盖率          18 / 18（100%）
  需求覆盖率              48 / 48（100%）
  可达性矩阵              2100 个组合：放通 748 / 阻断 1352
  故障注入检出            6 / 6（含过度放通 740 处隔离失效被全矩阵扫描抓出）
  生成配置                6 台设备 / 652 行，幂等（同拓扑重复生成逐字节一致）
```

## 一、这个工程解决什么问题

工厂网络运维有三个老大难，本工程各给一个解法：

| 老大难 | 现象 | 本工程的解法 |
| --- | --- | --- |
| **配置漂移** | 改过几次设备后，设备上配的与文档里写的对不上；换人接手只能逐台 `display` | 拓扑即数据源，配置全量生成；再把生成的配置**解析回结构**与拓扑逐条比对，闭环校验 |
| **变更靠人肉评估** | 加一条策略，谁也说不清会不会破坏既有隔离；只能改完再试，试错成本是停产 | 全量可达性矩阵 + 不变式扫描，**改配置前先预演**，报告直接说清哪些流受影响 |
| **校验不起作用也没人知道** | 写了检查脚本，但没人验证它真的能查出问题 | 故障注入：故意改坏拓扑，要求校验必须报错；报不出来说明校验有盲区 |

## 二、为什么这个项目值得放在简历上

面向**网络运维 / 网络工程 / 工业互联网 / 制造业 IT** 岗位。

GitHub 上的网络类项目绝大多数是「实验手册 + 配置截图」：配完拓扑截图交作业，
无法重复执行、无法验证、也无法证明配置是对的。本工程的差异：

| 常见做法 | 本工程 |
| --- | --- |
| 手工敲配置，截图留档 | 配置由 YAML + Jinja2 模板生成，**幂等可复现** |
| 用 ping / tracert 抽查几条链路 | 2100 个流量组合全量推导，每条结论可追溯到被拦的跳与策略 |
| 隔离要求写在文档里，靠人复核 | 隔离要求写成**不变式**，全矩阵扫描自动验证 |
| 验证脚本没有测试 | 用**故障注入**验证校验能力本身（等价于变异测试） |
| 只说「配置正确」 | 报告给出可达性矩阵量化快照，变更前后可 diff |

## 三、四个核心亮点

### 1. 配置即代码的闭环

```
   topology/smart_factory.yaml  （唯一数据源：设备/接口/VLAN/IP/路由/策略/NAT）
              │
              │ ① 结构自检        ← 数据本身的错误在这里拦下
              ▼
   generator.py + templates/*.j2
              │
              │ ② 生成 6 台设备的 VRP 配置（幂等）
              ▼
   output/configs/*.cfg
              │
              │ ③ 解析回结构
              ▼
   validator.py  ──── ④ 与拓扑逐条比对 ────► 不一致即报错
```

第 ③④ 步是这个闭环的关键：**只看生成器的输出是人眼审，几十台设备必然漏**。
把生成的配置反向解析回结构再比对，才是机器审。
本工程实测基线 6 台设备、652 行配置、0 处不一致。

### 2. 可达性矩阵：把「通不通」算出来

不做模拟器，也不发包，纯靠拓扑推导。给定「源主机 + 目的主机 + 服务（协议/端口）」，
按真实转发的优先级逐步判定：

```
一、同域 → 二层交换
    1.1 同一台接入交换机   → 直达
    1.2 跨接入交换机       → 两侧上行 Trunk 都必须放行该 VLAN
二、跨域 → 三层转发
    2.1 源侧二层到网关     → 接入交换机上行 Trunk 放行该 VLAN
    2.2 网关就绪           → VRRP 主备中至少一台核心有该 VLAN 的 SVI
    2.3 域间策略           → 按策略表顺序首条命中；无命中即隐式默认拒绝
    2.4 目的侧可达         → 内部域要求核心有该网段路由；互联网要求 NAT 覆盖该源域
```

实测矩阵（14 台内网主机 × 15 台目标 × 10 种服务 = 2100 个组合）：

| 源域 → 目的域 | 放通 | 阻断 | 说明 |
| --- | --- | --- | --- |
| 车间 → 服务器 | 100 | 100 | 只放通 MES/数据库/OPC UA/NTP/ICMP 五种 |
| 车间 → 办公 | 0 | 150 | 隔离要求 |
| 车间 → 互联网 | 0 | 100 | 生产网禁止出网（合规） |
| 办公 → 服务器 | 36 | 84 | 只放通 80/443/8080 |
| 办公 → 车间 | 0 | 150 | 隔离要求 |
| 服务器 → 车间 / 办公 | 0 / 0 | 200 / 120 | 防横向移动 |
| 服务器 → 互联网 | 80 | 0 | 经 NAT 下载补丁 |
| 管理 → 车间 | 15 | 35 | 只放通 SSH/SNMP/ICMP |
| 车间/办公/服务器 → 管理 | 0 | — | 管理方向不可逆 |

**关键点**：矩阵里每一格的放通数都应该能解释。某一格突然出现非预期放通，
就是策略被误改了——报告里的「放通占比」条一眼就能看出来。

### 3. 不变式：抓「抽查发现不了」的口子

逐条期望是点检查，只能覆盖关键业务流。隔离要求必须用**面检查**：

```yaml
- id: INV-001
  from_zone: workshop
  to_zone: office
  service: all
  expect: deny
  note: 生产网到办公网的所有主机、所有服务组合必须全部阻断
```

引擎会把该域对下的**全部主机 × 全部服务**组合跑一遍（不是抽查）。

本工程还专门处理了一种假通过：**不变式零匹配**。
如果不变式写错了域名或服务名，它会匹配到 0 个组合然后「通过」——
这和没写一样。引擎把零匹配单独识别并报出来。

### 4. 故障注入：证明校验能力不是摆设

注入 6 类故障，要求校验套件必须报错，并且**区分检出路径**：

| 编号 | 注入的故障 | 检出者 | 检出结果 |
| --- | --- | --- | --- |
| FLT-001 | 上行 Trunk 漏放行服务器 VLAN | 可达性 + 期望 | 8 条业务流失效 |
| FLT-002 | 误删车间到 MES 的放通策略 | 期望检查 | 4 条业务流失效 |
| FLT-003 | 临时放通写成 any→any permit | 不变式全矩阵扫描 | **740 处**隔离失效 |
| FLT-004 | 核心丢失服务器区网关 SVI | 结构自检 + 拒绝生成 | 配置下发不完整 |
| FLT-005 | 出口路由器 NAT 未启用 | NAT 推导 + 期望 | 2 条出网流失效 |
| FLT-006 | 办公接入口 VLAN 划错 | 结构自检 | 数据类错误 |

两条设计说明：

* **FLT-003 是重点**：管理员为临时放开一条业务写了 `permit ip`，单看某条业务流
  「通了」完全发现不了问题，只有全矩阵扫描才能暴露 740 处隔离失效。
* **FLT-006 只能靠结构自检**：可达性引擎按「域 → VLAN」映射推导，不依赖端口的实际 VLAN，
  所以数据类错误在行为检查里全绿。**只做行为检查会漏掉整类问题**，
  因此本工程把数据类与行为类分开检。

## 六、快速开始

```bash
# 一条命令：装依赖 → 生成配置 → 跑 50 条用例 → 出报告
python tools/make_report.py --run

# 变更预演（最有用的用法）：只校验不写盘
python tools/generate_configs.py --check-only

# 生成配置并导出可达性矩阵 CSV
python tools/generate_configs.py --matrix-csv

# 只跑某一类
pytest -m security          # 安全策略
pytest -m fault             # 故障检出
pytest -k TC-MTX-003        # 单条用例
```

Windows 双击 `run.bat`，Linux/macOS 用 `bash run.sh`。

## 九、已知边界与下一轮计划

| 边界 | 说明 | 下一轮 |
| --- | --- | --- |
| 不模拟真实协议栈 | 可达性靠拓扑推导，不生成真实报文 | 接 eNSP/GNS3 做一次交叉验证：推导结论与模拟器实测结果比对 |
| 只覆盖 IPv4 静态网络 | 无动态路由（OSPF/BGP）、无 IPv6 | 加 OSPF 邻居与区域校验；IPv6 双栈 |
| 无设备下发通道 | 只生成配置，不自动下发 | 加 Netmiko/Paramiko 下发，并对下发结果做二次回读校验 |
| 未做配置语法级校验 | 校验「与拓扑一致」，不校验 VRP 语法合法性 | 引入设备侧 `configuration replace` 预校验或语法树校验 |
| 无线、堆叠、BFD 未覆盖 | 当前为接入-核心-出口三层结构 | 按需扩展 |
| 无变更审批流 | 生成靠命令行 | 接 Git：拓扑变更走 PR，CI 跑全套校验后合并 |

## 十、诚信边界

* 拓扑、策略、设备型号均为**示例设计**，参考通用工厂网分层（接入-核心-出口）
  与等保三级「安全区域边界」要求，**不代表任何真实工厂的实际网络**。
* 设备型号（S5731 / S5735 / AR-6120）仅用于让配置看起来有载体；
  生成的配置为**标准 VRP 语法子集**，未经真机验证。首次上真机建议先做 `configuration replace`
  预校验，切勿直接覆盖运行配置。
* 可达性矩阵是**基于拓扑数据的推导结论**，不是实测结果。
  「推导说通」不等于「实测一定通」——真实网络还有生成树、MAC 表老化、
  策略路由等因素。这也是把「接模拟器交叉验证」列进下一轮计划的原因。
* 报告里的覆盖率数字由 `cases/checks.yaml` 与 `cases/requirements.yaml` 真实计算得出；
  校验能力清单必须完整登记，漏登记会让覆盖率虚高。
