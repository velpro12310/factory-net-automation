# 可达性验证原理

这份文档说明「通不通」是怎么算出来的，以及这套验证方法为什么可信。

---

## 一、为什么不用 eNSP / GNS3 模拟器

模拟器能跑真协议、结论可信，但它有两个致命问题：**慢** 和 **进不了 CI**。
大型拓扑启动一次几分钟，几十台设备的验证跑一轮半天，
结果是「变更前没人愿意跑」，工具形同虚设。

本工程选择**纯拓扑数据推导**：不打任何包，按真实转发的优先级逐步判定。
好处是：

* 2100 个流量组合的完整验证在 **0.7 秒**内跑完，可以放进每次提交
* 可以在**改配置之前**做预演——这是模拟器做不到的（模拟器要先有配置）
* 结论可追溯：每条 `deny` 都能说清被拦在哪一跳、命中了哪条策略

代价是「推导说通」不等于「实测一定通」（真实网络还有生成树、MAC 老化、
策略路由等因素）。所以「接模拟器做交叉验证」被列进了下一轮计划——
两种手段互补，而不是二选一。

---

## 二、推导顺序

顺序严格对齐真实转发的优先级：

```
输入：源主机 + 目的主机 + 服务（协议/端口）

一、同域 → 二层交换（不受域间策略约束）
    ├─ 同一台接入交换机        → 直达
    └─ 跨接入交换机            → 两侧上行 Trunk 都必须放行该 VLAN
         └─ 判定层级 = l2，policy_id = None

二、跨域 → 三层转发
    ├─ 2.1 源侧二层到网关      → 接入交换机上行 Trunk 是否放行源 VLAN
    ├─ 2.2 网关就绪            → VRRP 主备中至少一台核心有该 VLAN 的 SVI
    ├─ 2.3 域间策略            → 按策略表顺序首条命中；无命中即隐式默认拒绝
    └─ 2.4 目的侧可达          → 内部域：核心须有该网段路由 + 目的侧二层通
                                互联网：NAT 必须覆盖该源域
         └─ 判定层级 = l3
```

### 为什么把「策略」放在「目的侧可达」之前

排障时人最关心的是「这条业务流为什么被拦」。策略命中信息
（命中或拒绝了哪条规则、规则在说什么业务）比底层链路细节更有诊断价值。
所以策略检查在前——先给业务结论，再给技术细节。

### 为什么同域流量绕开策略表

同域流量在同一 VLAN 内二层交换，压根不经过三层网关，也就不会被网关上的
域间 ACL 处理。如果强行套用策略表，兜底的 `any → any 拒绝` 会把同域流量
全部误判为不通。

## 三、数据模型：什么决定可达性

推导只看这些字段，不依赖真实设备：

| 层 | 依赖的数据 |
| --- | --- |
| 二层 | 设备是否定义该 VLAN、接口 `allow_vlans`（Trunk）、接口 `vlan`（Access） |
| 三层 | 核心是否有该 VLAN 的 SVI、是否有目的网段路由、缺省路由指向 |
| 网关 | `vrrp_groups` 的主备、主备设备是否有 SVI 与 VRRP 实例 |
| 策略 | `security_policies`（含顺序）、`services`（协议与端口） |
| 出口 | `nat.enabled`、`nat.allowed_zones`、`nat.public_interface` |

**这意味着数据错会导致推导错**，所以结构自检必须前置：
连线不对称、接入口 VLAN 划错、VLAN 未定义等问题在生成配置之前就拦下，
避免「用错误的数据推出错误的结论，然后拿这个结论去指导变更」。

## 四、期望与不变式：点检查 + 面检查

### 期望（点检查）

逐条声明关键业务流，覆盖「设计意图里最重要的那些流」：

```yaml
- id: EXP-001
  src: PLC-01
  dst: MES-APP
  service: MES-WEB
  expect: permit
  note: 焊装线 PLC 向 MES 上报生产数据，必须放通
```

本工程共 25 条（17 放通 / 8 阻断）。

### 不变式（面检查）

表达普适要求，由引擎展开成「全部主机 × 全部服务」跑一遍：

```yaml
- id: INV-001
  from_zone: workshop
  to_zone: office
  service: all
  expect: deny
  note: 生产网到办公网的所有主机、所有服务组合必须全部阻断
```

本工程共 13 条。`INV-001` 一条就展开成 5×3×10 = 150 个流量组合。

### 为什么两者缺一不可

| | 只能发现 | 漏掉 |
| --- | --- | --- |
| 只有期望 | 列举到的问题 | 没列举的组合（某个主机、某个协议上的口子） |
| 只有不变式 | 类别性问题 | 单点业务流的放通遗漏（比如漏放某个端口） |

### 零匹配：最隐蔽的假通过

```
不变式写错了域名或服务名  →  匹配到 0 个流量组合  →  没有违反  →  「通过」
```

这和没写这条不变式完全一样，但报告上显示的是绿色。
本工程把零匹配单独识别为一个 `Violation`（`actual="no-match"`），强制报错：

```python
if matched == 0:
    violations.append(Violation(..., actual="no-match"))
```

## 五、配置回读：闭合「配置即代码」的回路

生成器可能「模板写错了但生成不报错」——漏放一个 VLAN、ACL 顺序被模板搞乱、
某台设备少下一条路由。只看生成器的输出是人眼审，几十台设备必然漏。

所以本工程把生成的配置**反向解析回结构**，再与拓扑逐条比对：

```
拓扑 YAML ──生成──► 设备配置 ──解析──► 结构化数据 ──比对──► 拓扑 YAML
    ▲                                                          │
    └────────────────── 不一致即报错 ──────────────────────────┘
```

校验项包括：设备名、VLAN 定义、接口类型/VLAN/地址、SVI 地址、VRRP 虚拟地址与优先级、
静态路由、ACL 条数与顺序、NAT 引用与顺序、运维配置（NTP / 日志服务器）。

实测基线：6 台设备、652 行配置、0 处不一致。

### 解析器的一个坑

配置里的段分隔注释必须重置解析上下文，否则「最后一个接口」的上下文会一直生效，
把后面的路由行当成接口子命令吞掉。本工程的接入交换机模板路由段注释带了括号后缀
（`# ---- 路由（管理流量默认网关）----`），早期用精确字符串匹配没命中，
导致三条静态路由全部解析不到、误报配置不一致。

修复方式是**任何以 `# ----` 开头的注释都重置上下文**，不再依赖精确匹配。

## 六、死规则检测

### 为什么要做

死规则 = 被前面规则完全覆盖、永远不会命中的规则。它不造成功能故障，
但**有害**：排障时按 ACL 顺序逐条读，会误以为这条规则在起作用，
而实际拦住流量的是上面那条。

### 判定方法

规则 A 覆盖规则 B（B 永远不可能命中）当且仅当 A 的匹配范围是 B 的超集：

| 维度 | A 覆盖 B 的条件 |
| --- | --- |
| 协议 | A 是 `ip`（any）或 A == B |
| 源地址 | A 是 any，或 A 的网段包含 B 的网段 |
| 目的地址 | 同上 |
| 目的端口 | A 未限定端口，或 A 与 B 端口相同 |

注意**与动作无关**：前面的规则无论是 permit 还是 deny，
只要范围是超集，后面的规则就永远执行不到。

### 平台陷阱

不能用 `ipaddress.ip_network(B) in ipaddress.ip_network(A)`：
Python 的 `IPv4Network.__contains__` 只认**严格子网**，`N in N` 返回 `False`。
用它会让「完全相同的两条规则」判不出覆盖，死规则检测静默失效——
本工程实测踩过这个坑（office 域有 3 条死规则没被识别）。

正确做法是显式比较地址范围：

```python
int(B.network_address) >= int(A.network_address) and \
int(B.broadcast_address) <= int(A.broadcast_address)
```

## 七、故障注入：验证「验证手段」本身有效

这是整套方法可信度的根据。核心问题：

> 你怎么知道这些检查真的能查出问题？

做法是故意把拓扑改坏，要求检查套件必须报错。注入 9 个变异算子：

| 算子 | 效果 |
| --- | --- |
| `remove_vlan_from_trunk_port` | 摘掉单个上行口的 VLAN（验证冗余兜得住） |
| `remove_vlan_from_all_trunks` | 摘掉全部上行的 VLAN（真断） |
| `delete_policy` | 删除一条策略 |
| `insert_catchall_permit` | 插入 any → any permit（最危险） |
| `remove_svi` | 删除 SVI（可指定单台或全部核心） |
| `change_svi_ip` | 改错网关地址 |
| `disable_nat` | 关闭 NAT |
| `misassign_access_port` | 接入口 VLAN 划错（数据类） |
| `remove_vlan_definition` | 删除 VLAN 定义（数据类） |
| `remove_static_route` | 删除静态路由 |

### 两类故障、两条检出路径

* **行为类**（漏放行 VLAN、误删 ACL、关 NAT）→ 由可达性矩阵与期望检查检出
* **数据类**（接入口 VLAN 划错、VLAN 未定义）→ 由拓扑结构自检检出

**为什么必须分开**：可达性引擎按「域 → VLAN」映射推导，不依赖端口的实际 VLAN，
所以接入口 VLAN 划错在行为检查里**全绿**。只做行为检查会漏掉整类问题。

### 一个刻意的设计：区分「业务影响」与「配置正确性」

删除**一台**核心的 SVI，在真实环境会触发备设备接管，业务**不受影响**。
如果可达性引擎把它判为不可达，就会出现「网络其实是通的，工具却报不通」的误报——
误报多了就没人信工具了。

所以本工程的口径是：

| 情形 | 判定 |
| --- | --- |
| 主备中至少一台有 SVI | 可达性判 **通**（备份接管） |
| 两台核心都没 SVI | 可达性判 **不可达**（无路由） |
| 主设备缺 SVI | 可达性判通，但**结构自检报错**（配置下发不完整） |

这条区分由 `TC-L3-003` 验证，是本工程里最能体现思考深度的地方之一。

## 八、局限与诚实的边界

| 局限 | 影响 | 缓解方式 |
| --- | --- | --- |
| 不模拟真实协议栈 | 推导结论非实测结论 | 下一轮接 eNSP 做交叉验证 |
| 无动态路由 | OSPF/BGP 收敛相关的可达性算不出 | 明确列为未覆盖范围 |
| 无 STP 环路计算 | 冗余链路在二层可能被 STP 阻断 | 接入端口配置 `stp edged-port` 规避 |
| 不校验 VRP 语法 | 生成的配置语法有误时不自知 | 首次上真机先用 `configuration replace` 预校验 |
| 单播为主 | 广播/组播的可达性未建模 | 需用时单独扩展 |

**原则**：工具能说什么、不能说什么，必须写在文档里。
一个声称「什么都能验证」的工具，实际可信度为零。
