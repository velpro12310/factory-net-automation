# 拓扑与规则说明

这份文档说明拓扑「为什么这么设计」。面试问「你这个网络是怎么规划的」时照这个讲。

---

## 一、总体架构：接入 - 核心 - 出口 三层

```
                        互联网（供应商云 / 补丁源）
                                │
                    ┌───────────┴───────────┐
                    │      RT-EGRESS        │  AR-6120  出口路由器（NAT）
                    │  198.51.100.2/30      │
                    └──┬──────────────┬─────┘
              10.10.88.0/30    10.10.88.4/30
                       │              │
        ┌──────────────┴──┐        ┌──┴──────────────┐
        │   Core-SW-1     │        │   Core-SW-2     │  S5731  核心（VRRP 主 / 备）
        │  10.10.40.251   │        │  10.10.40.250   │
        └──┬────┬────┬────┘        └────┬────┬────┬──┘
           │    │    │   10.10.99.0/30   │    │    │
           │    │    └─────── 核心互联 ──┘    │    │
           │    │                             │    │
      ┌────┴┐ ┌─┴───┐                    ┌────┴┐ ┌─┴───┐
      │ACC- │ │ACC- │                    │ACC- │ │ACC- │
      │WORK │ │OFFI │                    │SERV │ │OFFI │  S5735  接入（双上联）
      └──┬──┘ └──┬──┘                    └──┬──┘ └──┬──┘
         │       │                          │       │
    PLC/机器人  办公终端              MES/数据库  备网管
    HMI/工程师站 打印机                 OPC UA/NTP  主网管
```

**为什么三层而不是两层**：工厂网里生产设备与办公终端的安全等级完全不同，
必须做区域隔离；隔离只能在三层做（二层只能靠 VLAN，无法做策略）。
把网关集中在核心，接入层只做二层转发，好处是**域间策略只有一处生效点**，
排查 ACL 时不用逐台设备找。

## 二、安全域与 VLAN 规划

| 域 | VLAN | 网段 | 网关（VRRP 虚拟） | 内容 |
| --- | --- | --- | --- | --- |
| 车间生产区 | 10 | 10.10.10.0/24 | 10.10.10.254 | PLC、机器人控制器、HMI、工程师站 |
| 办公区 | 20 | 10.10.20.0/24 | 10.10.20.254 | 办公终端、打印机 |
| 服务器区 | 30 | 10.10.30.0/24 | 10.10.30.254 | MES 应用、数据库、OPC UA 网关、NTP |
| 设备管理区 | 40 | 10.10.40.0/24 | 10.10.40.254 | 网络设备管理口、主备网管服务器 |
| 核心互联 | 99 | 10.10.99.0/30 | — | 两台核心之间的链路 |

### 三个规划决策

**① 管理与业务分离（VLAN 40）**
网络设备的管理地址单独划一个 VLAN，不与管理服务器以外的任何区域互通。
好处是即使业务网被攻破，攻击者也进不了设备管理面。

**② 服务器区不划子域**
MES 应用、数据库、OPC UA 网关放在同一个 VLAN 30。这是刻意的简化：
它们之间流量密集且互相依赖（应用连数据库、网关连数据库），
再插一层 ACL 只会增加排障复杂度而对安全收益有限。
安全边界划在「服务器区与外界之间」，而不是「服务器区内部」。

**③ 每台接入交换机双上联**
`ACC-WORKSHOP / ACC-OFFICE / ACC-SERVER` 各有两条上行 Trunk，
分别连到 Core-SW-1 与 Core-SW-2，配合 VRRP 主备，任意一条链路或一台核心故障
都不影响业务。这条设计有多条用例验证，其中 `TC-AVL-003` 用故障注入证明它真的生效。

## 四、安全策略表

### 4.1 排序规则（最容易出错的地方）

策略表按 **id 升序**匹配，首条命中生效。排列必须遵循：

```
具体放通  →  具体拒绝  →  出网放通  →  兜底拒绝
 10~32       40~47        50~51        90
```

**为什么出网放通必须排在最后**：出网策略的目标是「互联网」，而 ACL 里无法直接表达
「非内网地址」，只能渲染成 `permit ip`（目标 any）。这是一条 catch-all 规则，
如果排在拒绝规则之前，会把后面所有内网拒绝规则全部遮蔽——隔离要求集体失效。

这个坑在本工程开发过程中真实踩到过：最初把 `office → internet permit` 和
`server → internet permit` 排在 id 21/22，结果 `server → office deny`（id 47）
被完全遮蔽，服务器区可以访问办公区。是**全矩阵扫描**把它抓出来的
（见 `INV-012` 的注释）。现在这两条策略编号改成 50/51，排到所有拒绝之后。

### 4.3 「SNMP 写成 TCP」——一个被工具抓出来的真实错误

策略 30 最初写成 `tcp ports: [22, 161]`。结果 SSH(22) 通了，SNMP 不通——
因为 **SNMP 走 UDP 161**，而 ACL 里协议不匹配就是不匹配，端口号对不上没有任何用。

这个问题是怎么发现的：跑完全量矩阵后看「管理区 → 车间」的放通数是 10，
而按设计应该是 15（SSH + SNMP + ICMP 各 5 台主机）。
差 5 条正好是 SNMP 那一档，顺藤摸瓜找到协议写错。

修复方式是把策略拆成 30(tcp 22) / 31(icmp) / 32(udp 161) 三条，
并补了一条期望 `EXP-043` 专门盯住 SNMP 的可用性。
**这类错误的教训是：网络策略必须按协议分别定义，不能把不同协议的端口混在一行。**

## 五、ACL 的生成与规范化

策略表是「意图」，ACL 是「设备上的落地」。生成分三步：

1. **展开**：一条策略若写了多个端口，拆成多条只匹配单端口的规则（语义最清晰）
2. **剔死规则**：被前面规则完全覆盖、永远不会命中的规则直接剔除
3. **编号**：按 5 为步长重新编号，留出后续插规则的余量

每个安全域对应一个高级 ACL，应用在该域 Vlanif 的入方向：

| 域 | ACL 编号 | 应用位置 |
| --- | --- | --- |
| 车间 | 3010 | Core-SW-1/2 的 `Vlanif10` inbound |
| 办公 | 3020 | Core-SW-1/2 的 `Vlanif20` inbound |
| 服务器 | 3030 | Core-SW-1/2 的 `Vlanif30` inbound |
| 管理 | 3040 | Core-SW-1/2 的 `Vlanif40` inbound |

### 关于「死规则」

本拓扑中有 1 条死规则：车间域 ACL 里的 `any → mgmt 拒绝`（策略 46）。
它被更具体的 `车间 → 管理 拒绝`（策略 43）完全覆盖，永远不会命中。

死规则**不造成功能故障**，但它有害：排障时按 ACL 顺序逐条读，
会误以为「这条规则在起作用」，而实际上拦住流量的是上面那条。
所以本工程把它剔除，并在报告里单列，而不是让它默默留着。

> 术语提醒：判断「规则 A 是否覆盖规则 B」时，不能用 Python 的
> `ip_network(B) in ip_network(A)`——它只认**严格子网**，`N in N` 返回 `False`，
> 会导致完全相同的两条规则判不出覆盖，死规则检测静默失效。
> 本工程改用显式地址范围比较（见 `acl._prefix_covers`）。

## 六、NAT 出口

```
内网源网段（只允许这两个）        公网口
  10.10.20.0/24  办公区   ─┐
                            ├─► ACL 2000 ─► nat outbound 2000（Easy IP / PAT）
  10.10.30.0/24  服务器区 ─┘     在 GigabitEthernet0/0/3 上
```

**两个必须同时满足的条件**：出网流量既要被**策略放通**（策略 50/51），
又要被 **NAT 覆盖**（源域在 `allowed_zones` 内）。只满足一个都不通——
这也是「加了策略忘了加 NAT 地址池」这类故障的根源，`TC-ACL-005` 与 `TC-NAT-003`
分别盯着这两个条件。

**为什么车间与管理区不在地址池内**：这是一个安全要求而不是可用性要求。
生产网一旦有出网通道，就存在数据外传与远程控制的可能，
对汽车零部件工厂来说这是合规红线。所以 NAT 地址池只含办公区与服务器区两个网段。

**生成顺序**：ACL 必须先定义、再被 `nat outbound` 引用，否则设备会报
「引用的 ACL 不存在」。这一点由 `TC-NAT-004` 校验生成配置里的先后顺序。
